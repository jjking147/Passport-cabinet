## 一、项目概述

基于 **GD32F407VET6**（512KB Flash，8MHz HXTAL → 168MHz 主频）实现的固件空中升级（OTA）示例，采用 **A/B 双区 + 回滚** 的经典 IAP 架构，升级数据通过 **USART + YMODEM(1K, CRC16)** 下发。

**能力清单：**

| 能力 | 说明 |
|---|---|
| A/B 双区 | 固件轮换写入 Bank A / Bank B，升级时永远不覆盖「可运行的好版本」 |
| 升级回滚 | 新固件连续 `TRY_LIMIT(5)` 次启动未被自身确认 → 自动切回另一槽 |
| 完整性校验 | 整镜像 CRC32 + YMODEM 每块 CRC16 双重校验 |
| 掉电安全 | 先烧非活动槽，中途掉电只损坏目标槽，旧版本仍在 |
| 双串口隔离 | 日志（USART0）与下载（USART1）分开，调试和升级互不干扰 |

**技术栈：**

- 固件库：`GD32F4xx_Firmware_Library_V3.2.0`（标准外设库，FMC 闪存 + RCU 时钟）
- 工具链：Keil MDK + ARMCC AC5（V5.06），器件包 `GigaDevice.GD32F4xx_DFP 3.0.3`
- 上位机：Python 3 + `pyserial`（`tools/` 下三个脚本）

## 二、Flash 分区（A/B 双区 + 回滚）

GD32F407VET6 = 512KB Flash（`0x08000000` ~ `0x0807FFFF`），扇区布局与 STM32F407 一致：

| 扇区 | 大小 | 地址范围 |
|---|---|---|
| 0 | 16KB | 0x08000000 |
| 1 | 16KB | 0x08004000 |
| 2 | 16KB | 0x08008000 |
| 3 | 16KB | 0x0800C000 |
| 4 | 64KB | 0x08010000 |
| 5 | 128KB | 0x08020000 |
| 6 | 128KB | 0x08040000 |
| 7 | 128KB | 0x08060000 |

**本项目分区：**

| 区域 | 扇区 | 大小 | 地址范围 | 作用 |
|---|---|---|---|---|
| **Bootloader** | 0~2 | 48KB | `0x08000000` ~ `0x0800BFFF` | IAP 引导器（复位入口） |
| **BootMgr** | 3 | 16KB | `0x0800C000` ~ `0x0800FFFF` | 启动记录（A/B 状态、CRC） |
| **Bank A** | 4~5 | 192KB | `0x08010000` ~ `0x0803FFFF` | 应用镜像区 A |
| **Bank B** | 6~7 | 256KB | `0x08040000` ~ `0x0807FFFF` | 应用镜像区 B（示例只用前 192KB） |

- `APP_MAX_SIZE = 192KB`（取 A/B 较小者）
- 分区常量只在 [`common/ota_config.h`](common/ota_config.h) 定义一处，Bootloader 与 App **必须一致**。
- App 镜像 A/B 分别链接到 `0x08010000` / `0x08040000`，运行靠 `SCB->VTOR = APP_ADDR` 重定位向量表。

## 三、硬件接线

| 端口 | 外设 | MCU 引脚 | 方向 | 接对端 |
|---|---|---|---|---|
| **日志口** | USART0 | PA9 | TX（打印） | USB-TTL #1 的 RX |
| | | PA10 | RX（收 'O' 命令） | USB-TTL #1 的 TX |
| **下载口** | USART1 | PA2 | TX（回 ACK/NAK） | USB-TTL #2 的 RX |
| | | PA3 | RX（收 hex 数据） | USB-TTL #2 的 TX |

- 串口参数：两路都 **9600-8-N-1**，无流控
- 指示灯：PF9（ALIENTEK 开发板 DS0 惯例，可按实际板子改）

> 记忆口诀：MCU 的 TX 接对端的 RX。这两对引脚都是交叉接。

## 五、核心机制

### 5.1 启动记录（BootMgr 扇区）

```c
typedef struct {
    uint32_t magic;         // "OTAB" 魔数
    uint32_t active_slot;   // SLOT_A(0) / SLOT_B(1)
    uint32_t state[2];      // ST_INVALID(0) / ST_CONFIRMED(1) / ST_TRYING(2)
    uint32_t try_count;     // 当前 trying 槽已尝试启动次数
    uint32_t request;       // REQ_NONE / REQ_UPDATE
    uint32_t app_size[2];   // 每槽镜像大小
    uint32_t app_crc[2];    // 每槽整镜像 CRC32
} boot_record_t;
```

三态状态机的关键：`ST_TRYING`（刚烧录待确认）→ App 调 `bootmgr_confirm()` → `ST_CONFIRMED`；超过 `TRY_LIMIT` 次没确认 → 判为坏固件 → 回滚。

### 5.2 Bootloader 引导流程

1. 读启动记录；无有效记录则初始化
2. `request == REQ_UPDATE` → 进入 OTA 下载
3. 活动槽 `CONFIRMED` → 校验 CRC32 → 跳转
4. 活动槽 `TRYING` → `try_count++` → 达 `TRY_LIMIT` 则回滚到另一槽
5. 无有效 App → 进入 OTA（失败则循环重试）

### 5.3 OTA 目标槽选择（四分支，避免覆盖好版本）

```
只有 A 是 CONFIRMED  -> 烧 B
只有 B 是 CONFIRMED  -> 烧 A
两槽都无效(首次)     -> 烧 A     ← 关键：保证首次发 App_A.hex 就烧到 Bank A
两槽都 CONFIRMED     -> 烧非活动槽 (A/B 交替升级)
```

### 5.4 OTA 下载流程

1. 擦除目标槽（FMC 按扇区）
2. `ymodem_receive()` 逐包写入 + 校验
3. 整镜像 CRC32 → 写启动记录（目标槽 `ST_TRYING`，切换 `active_slot`）
4. `NVIC_SystemReset()` → 下一次引导跳到新槽

### 5.5 App 侧

- `main()` 首行 `SCB->VTOR = APP_ADDR`（A/B 任意槽可运行的关键）
- 正常启动后 `bootmgr_confirm()` 标记本槽 `CONFIRMED`
- 日志口收到字符 `O` → `bootmgr_request_update()` + 复位 → 回 Bootloader 进入 OTA
- 启动横幅 `===== OTA APP-X =====` + 每 2 秒 `[APP-X] alive @0x...` 心跳，用于无 LED 环境下区分当前 Bank

## 六、使用速查

### 首次全流程

```bash
# 1. Bootloader.hex 烧到 0x08000000
# 2. 上电，日志口看到 "Erase bank A" + "Waiting YMODEM"
python tools/ymodem_send.py --port COM7 --baud 9600 --file App/OBJ/App_A.hex
# 3. 复位自动跳 Bank A 运行
```

### 日常升级

日志口敲 `O` → App 复位进 Bootloader → 按 `Erase bank X` 发对应 hex。

### 触发回滚演示

把 `App/USER/main.c` 的 `APP_SIMULATE_BAD` 置 1 → 烧成坏固件 → 断电重启 5 次 → 自动切回好版本。

## 七、踩坑记录与解决方法（重点）

> 以下是本套代码从「能编过」到「能真机跑通」过程中遇到的全部问题。每个都记录了**现象 / 根因 / 修复**。

### 坑 1：首次 OTA 目标槽选错（`Erase bank B`）

- **现象**：全新芯片首次 OTA，串口打印 `Erase bank B`。若按此发 `App_A.hex`（链接 `0x08010000`），固件被写进 Bank B，跳转必 HardFault。
- **根因**：`ota_target_slot()` 里「两槽都无效」的情况，被「active==A → 烧非活动槽=B」的分支误捕。
- **修复**：改为四分支明确判断（见 5.3），「两槽都无效 → 烧 A」摆在「都好 → 烧非活动」之前。

### 坑 2：YMODEM `C` 握手竞态（脚本报「等待 'C' 超时」）

- **现象**：`ymodem_send.py` 卡在 `[1] 等待接收端 'C'`，30 秒超时。
- **根因**：Bootloader 只在进入等待时**发一次** `C`，之后超时改发 `NAK`；脚本死等 `C`，启动晚了就再也等不到 `C`。
- **修复**：
  1. 等待期间**反复发 `C`**（每个超时周期都发）；
  2. 去掉多余的二次 `C` 握手（改成 ACK 完文件名块直接发数据，更贴合标准）；
  3. Bootloader 升级失败改为**循环重试**，而非整机复位。

### 坑 3：1ms 轮询导致串口丢字节（`hello` → `ho`）

- **现象**：回显测试发 `hello`，两个接收区收到 `ho`——首尾字符对、中间字符丢。
- **根因**：`ota_dl_recv_byte()` / `ota_log_recv_byte()` 每次轮询 `delay_us(1000)`（1 毫秒）。115200 波特率下字节间隔仅 **87µs**，1 毫秒内涌入约 11 个字节，而 UART 接收缓冲只有 2 字节深 → **溢出错乱丢字节**。
- **修复**：轮询粒度从 `delay_us(1000)` 改成 `delay_us(10)`（10µs），并相应调整超时计数。
- **额外影响**：这个 bug 同样会毁掉真正的 YMODEM 下载（1024 字节块会整块 CRC 失败），属于致命级。

### 坑 4：漏回 ACK，每个块都重发（`重发块 1/2/3/4`）

- **现象**：升级能成，但 python 打印 `-> 重发块 1/2/3/4`，每个块白等 5 秒。
- **根因**：`ymodem.c` 收到数据块、写完 flash 后**忘了发 ACK**；发送端 5 秒超时重发，重发包恰好撞上「去重」分支才被 ACK，属于「侥幸能跑」。
- **修复**：写完块成功后补一句 `ota_dl_send_byte(ACK)`。
- **影响**：小固件（4 块）多花约 20 秒；大固件（几百块）会慢到不能接受。

### 坑 5：波特率从 115200 下调到 9600

- **原因**：用户倾向更保守、更抗干扰的波特率。实测 App 仅 ~4KB，9600（约 1KB/s）约 4 秒传完，完全可接受。
- **结果**：两路串口统一 `9600-8-N-1`；坑 3 的丢字节 bug 已修，但 9600 让字节间隔从 87µs 放宽到 1.04ms，余量更大。

### 坑 6：串口助手与脚本的端口独占冲突

- **现象**：早期单口设计（日志/下载共用 USART0），串口助手和 Python 脚本无法同时打开同一 COM 口。
- **修复**：拆成两路串口——日志 USART0（PA9/PA10）+ 下载 USART1（PA2/PA3），互相独立，日志助手可常开。

### 坑 7：编译 warning「文件末尾缺换行」

- **现象**：首次编译 22 个 `#1-D: last line of file ends without a newline`。
- **根因**：自动生成的文件末尾没有换行符，纯格式问题，不影响功能。
- **修复**：给所有缺失文件补尾部换行，编译归零 warning。

### 坑 8：LED 看不到 / 引脚约定

- **现象**：用户看不到 LED 闪烁（代码按 ALIENTEK 惯例用 PF9）。
- **处理**：改用**日志口区分 Bank**——启动横幅 `===== OTA APP-X =====` + 每 2 秒 `[APP-X] alive @0x...` 心跳，无需看灯。LED 引脚可后续按实际板子调整。

### 坑 9：历史遗留（LiftV1.6 的 app_addr 越界）

- **现象**：LiftV1.6 的 `bll_main.c` 里 `app_addr = 0x080e0000`（≈896KB），超出 512KB 闪存，IAP 跳转必 HardFault。
- **结论**：本套分区使用正确的 `0x08010000` / `0x08040000`。若沿用旧工程，需把该值改掉。

## 八、寄存器/时钟要点（GD32F407 速记）

- 内核：Cortex-M4 + FPU，NVIC 4 位优先级
- 时钟：HXTAL 8MHz → PLL（PSC=8, N=336, P=2）→ **SYSCLK 168MHz**；AHB=168M，APB2=84M，APB1=42M
- USART0 在 APB2（84M），USART1 在 APB1（42M），`usart_baudrate_set()` 内部用 `rcu_clock_freq_get()` 自动读分频，无需手工算
- 闪存编程走 **FMC**：`fmc_unlock()` / `fmc_sector_erase(CTL_SECTOR_NUMBER_x)` / `fmc_word_program()` / `fmc_lock()`
- **`fmc_page_erase()` 只有 425/427/470 支持，407 只有扇区擦除**，因此分区必须对齐扇区边界（最小 16KB）

## 九、经验教训总结

1. **串口流式接收绝不能用毫秒级轮询**。UART 是没有流控的，高速率下「睡一觉」必然溢出。收流数据必须用中断 + 环形缓冲，或至少微秒级轮询。
2. **协议握手要「可重入」**。任何「只发一次就死等」的握手指令（如 YMODEM 的 `C`）都会有竞态，等待方要持续重发。
3. **每个数据块的 ACK 是硬约束**，缺了会让对端走超时重传，功能看起来「能跑」但慢得离谱、隐蔽性极强。
4. **A/B 换区必须意识到位置相关代码**。同一份 ARM 代码不能跑两个地址，必须分两个 Target 编译（`App_A` / `App_B`），且发错槽的 hex 会 HardFault。
5. **「能编过」≠「能真机跑通」**。真正的坑（目标槽、竞态、丢字节、漏 ACK）全都只能靠真机 + 串口日志暴露出来。回显测试 + 波特率扫描这类小工具，排查效率极高。
