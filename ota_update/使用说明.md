# GD32F407 OTA/IAP 使用说明（含烧录顺序）

> 本文回答两个核心问题：**先烧哪个**、**怎么一步步用起来**。
> 配套代码见 `common/`、`Bootloader/`、`App/`、`tools/`；分区与原理见 `README.md`。

---

## 0. 一句话结论

**先烧 Bootloader，App 永远通过 OTA 灌进去。**

原因：Cortex-M4 上电后从 Flash 最低地址 `0x08000000` 取复位向量。Bootloader 链接在 `0x08000000`，是系统能跑起来的起点；App 链接在 `0x08010000`/`0x08040000`，脱离 Bootloader 无法单独启动。

新芯片 / 擦空后的芯片，正确顺序是：

```
第一步  烧 Bootloader.hex  ->  0x08000000
第二步  上电，串口看到 "Waiting YMODEM ..."
第三步  运行 ymodem_send.py 发 App_A.hex  (自动写入 Bank A)
第四步  复位后自动跳 Bank A 运行
```

> ⚠️ **App 不要用烧录器裸烧**。因为 Bootloader 靠「启动记录扇区」判断哪个槽有有效固件，直接裸烧 App 不会更新启动记录，Bootloader 上电后仍认为"无有效 App"。App 必须通过 OTA 流程写入（或同时手动初始化启动记录）。

## 1. 硬件与接线

| 项目 | 说明 |
|---|---|
| 目标板 | GD32F407VET6，板载 **8MHz** 晶振（与 LiftV1.6 一致） |
| 调试/烧录器 | J-Link / ST-Link / DAP-Link，接 SWD（SWDIO、SWCLK、GND） |
| 日志串口 | **USART0**：`PA9` = TX（打印日志），`PA10` = RX（收 'O' 命令），接 USB-TTL #1，共地 GND |
| 下载串口 | **USART1**：`PA2` = TX（回 ACK/NAK），`PA3` = RX（收 hex 数据），接 USB-TTL #2，共地 GND |
| 串口参数 | 两路都 **9600-8-N-1**，无流控 |
| 指示灯 | PF9（ALIENTEK/GD32 板 DS0），App 运行时心跳闪烁 |

> 两路串口分工：**日志走 USART0、下载走 USART1**，互不干扰，日志串口助手可以**一直开着**看打印。`O` 升级命令从日志口（USART0）键入，hex 从下载口（USART1）下发给 `ymodem_send.py`。

## 2. 三个镜像的关系

| 镜像 | 链接地址 | 干什么 | 谁生成 |
|---|---|---|---|
| `Bootloader.hex` | `0x08000000` | 引导 + YMODEM 收固件 + 跳转/回滚 | `Bootloader` 工程 |
| `App_A.hex` | `0x08010000`(Bank A) | 业务固件，跑在 A 槽 | `App` 工程的 `App_A` Target |
| `App_B.hex` | `0x08040000`(Bank B) | 业务固件，跑在 B 槽 | `App` 工程的 `App_B` Target |

**核心规则：看到串口打印 `Erase bank A` 就发 `App_A.hex`，看到 `Erase bank B` 就发 `App_B.hex`。** 位置相关代码，发错槽的 hex 会跳转 HardFault。

## 3. 编译

前置：Keil MDK 已装 `GigaDevice.GD32F4xx_DFP 3.0.3`（LiftV1.6 模板同款）。

1. 打开 `Bootloader/USER/Bootloader.uvprojx` → **Build** → 产出 `Bootloader/OBJ/Bootloader.hex`
2. 打开 `App/USER/App.uvprojx`，切 Target：
   - `App_A` → Build → `App/OBJ/App_A.hex`
   - `App_B` → Build → `App/OBJ/App_B.hex`

> 两个 App Target 只差"链接地址"和 `-DAPP_ADDR`，源码共用。

## 4. 烧录步骤

### 场景 A：全新芯片 / 擦空（第一次，最标准）

**Step 1 — 烧 Bootloader**
- 方式一（推荐）：Keil 打开 `Bootloader.uvprojx`，配好下载器后点 **Download**，勾选下载到 Flash（`0x08000000`，512KB）。
- 方式二：用 J-Flash / DAPLink 直接加载 `Bootloader/OBJ/Bootloader.hex` 烧录。

**Step 2 — 上电看串口**
串口助手（9600-8-N-1）应看到：

```
=== GD32F407 OTA Bootloader ===
  Bank A @0x08010000 state=0x00000000 size=0x00000000 crc=0x00000000
  Bank B @0x08040000 state=0x00000000 size=0x00000000 crc=0x00000000
active=A
No valid app, enter OTA.
Erase bank A ...
Waiting YMODEM (CRC, 1K) transfer...
```

> 注意 `state=0x00000000` 表示两槽都 INVALID；`Erase bank A` 表示 Bootloader 要烧 Bank A。

**Step 3 — 发 App_A.hex**
另开一个终端（同一台或另一台电脑接同一串口）：

```bash
pip install pyserial
python tools/ymodem_send.py --port COM3 --baud 9600 --file App/OBJ/App_A.hex
```

（`COM3` 改成你实际的串口号。Windows 下常见 `COM3~COM9`，可用设备管理器确认。）

**Step 4 — 观察结果**
Bootloader 串口继续打印：

```
Received 0x00003ABC bytes, crc=0xXXXXXXXX
Update boot record ...
Success. Rebooting ...
```

复位后自动跳入 Bank A，App 开始运行：

```
=== GD32F407 OTA App (Bank A) ===
Boot confirmed.
Type 'O' to request OTA upgrade.
```

同时 PF9 灯开始闪烁。至此第一次升级完成。

### 场景 B：日常升级（已有 App 在跑）

1. 在 App 的串口连接里**发送字符 `O`**（单字母，不用回车）
2. App 打印 `OTA requested, reboot to bootloader...` 并复位
3. Bootloader 打印 `Update requested.` → `Erase bank B ...` → `Waiting YMODEM ...`
4. 看到 `Erase bank B` → 运行 `ymodem_send.py` 发 **`App_B.hex`**
5. 完成后自动跳 Bank B 运行

## 5. 串口日志对照表（排错用）

| 打印 | 含义 | 你该做什么 |
|---|---|---|
| `No valid app, enter OTA.` | 两槽都无有效固件 | 准备发 App_A.hex |
| `Erase bank A ...` | 本次 OTA 目标是 Bank A | 发 App_A.hex |
| `Erase bank B ...` | 本次 OTA 目标是 Bank B | 发 App_B.hex |
| `Waiting YMODEM (CRC, 1K) transfer...` | 正在等 YMODEM 数据 | 运行 ymodem_send.py |
| `Received 0x... bytes, crc=0x...` | 收齐且 CRC32 校验通过 | 无需操作 |
| `Success. Rebooting ...` | 升级成功，即将复位跳转 | 等跳转 |
| `Jump to A` / `Jump to B` | 正常跳转 | 无需操作 |
| `Active image CRC mismatch!` | 活动槽 CRC 校验失败 | 会进 OTA 重刷 |
| `Try limit reached, rollback!` | 新固件连续 5 次未确认，回滚 | 观察是否回到旧版本 |

## 6. A/B + 回滚 完整演示

> 熬一遍能彻底理解机制，建议按顺序做一次。

1. **灌 Bank A**：场景 A 的 Step 1~4 → 最终跑 `App( Bank A )`
2. **升级到 B**：发 `O` → 发 `App_B.hex` → 跑 `App( Bank B )`
3. **再升回 A**：发 `O` → 发 `App_A.hex` → 跑 `App( Bank A )`（两槽现在都是 CONFIRMED，Bootloader 交替烧非活动槽）
4. **模拟"坏固件"验证回滚**：
   - 打开 `App/USER/main.c`，把 `#define APP_SIMULATE_BAD 0` 改成 `1`，重新 Build `App_B` 得到"坏" `App_B.hex`
   - 发 `O` 升级到 B（坏固件）
   - 坏固件启动后**不调用 `bootmgr_confirm()`**，直接死循环闪灯
   - 反复断电/复位，每次 Bootloader 都 `Try ...` 跳入坏固件
   - **第 5 次**启动时 Bootloader 打印 `Try limit reached, rollback!`，自动切回 Bank A 的好版本
   - 验证完成后把 `APP_SIMULATE_BAD` 改回 `0`

## 7. 常见问题排查

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 串口收到乱码 | 板载晶振不是 8MHz，PLL 时钟错误 | 改 `App/USER/gd32f4xx.h` 的 `HXTAL_VALUE` 和 `system_gd32f4xx.c` 的 PLL 档位 |
| 一直 `Waiting YMODEM` 但发不进去 | 串口 RX/TX 接反、波特率不对、未共地 | 短路 TX/RX 用串口助手自收发验证接线 |
| `YMODEM receive FAILED!` | 发送途中超时/重传次数耗尽 | 先复位进 Bootloader 再立刻启动脚本 |
| 跳转后卡死/HardFault | 发错槽的 hex（`App_A` 发到了 Bank B） | 严格按 `Erase bank X` → 发 `App_X.hex` |
| Boot 后一直 `No valid app` | 直接裸烧了 App，启动记录没登记 | 走 OTA 流程重刷 |
| `Boot confirm FAILED!` | 启动记录扇区擦写失败 | 检查 FMC 是否被写保护/读保护 |

## 8. 生产环境注意

1. **`bootmgr_confirm()` 时机**：本示例 App 启动即确认。生产上应等 **自检通过 / 关键外设初始化成功 / 收到主机握手** 后再确认，避免"能跑但半死不活"的固件被当成好版本。
2. **掉电保护**：A/B + 先烧非活动槽的机制天然保证——升级中途掉电，最多损坏正在烧的槽，另一槽的好版本仍在，重启回退即可。
3. **整镜像 CRC32**：写入前算、启动时校验，能拦住半截/损坏固件。但注意大镜像（>100KB）启动校验会占用几十毫秒，量大可考虑只对关键段校验或上硬件 CRC。
4. **中断向量**：App 必须 `SCB->VTOR = APP_ADDR`。若你在 App 里加了中断，漏掉这行会导致中断跑进 Bootloader 的向量表。
5. **继续修复历史遗留**：`LiftV1.6` 的 `bll_main.c` 里 `app_addr = 0x080e0000` 越界（512KB 芯片），沿用本套分区时应改成 `0x08010000`。
